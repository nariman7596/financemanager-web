# The sync protocol

Server side, as implemented. Phase 7 builds the client engine against this
contract.

## The three properties

1. **The server assigns order.** Device clocks are wrong — phones cross time
   zones, users change the date — so ordering comes from
   `Household.syncRevision` and nothing else. Every write that a device must
   learn about takes a number from it.
2. **Every push is idempotent.** A batch retried after a timeout applies once.
   The client generates an `opId` per mutation and the server records it in
   `SyncOperation`.
3. **Nothing is silently discarded.** A write that loses a conflict is kept in
   `SyncConflict` and shown to the user. This is a ledger; a figure somebody
   typed does not just vanish.

## Pull

```
GET /api/v1/sync/changes?since=<cursor>&limit=500
    Authorization: Bearer <access token>
    X-Household-Id: <household>        (a preference; membership is verified)
    X-Device-Id: <device>              (optional; lets tombstones be swept)

→ { changes: [ { entity, id, revision, deletedAt, ...fields } ],
    nextCursor: "<revision>:<id>",
    hasMore: boolean }
```

The cursor is **opaque**: store it verbatim, do not parse or compare it. It is
`(revision, id)` because rows seeded when a household is created all share one
revision — a cursor on revision alone would let a page boundary fall inside
that group and skip the rest of it.

Tombstones are included. A delete is a change a device has to learn about.

Loop until `hasMore` is false, applying each page in one local transaction.

## Push

```
POST /api/v1/sync/push
{ deviceId, ops: [ { opId, entity, id, op: "upsert"|"delete",
                     baseRevision?, payload? } ] }

→ { applied: [{opId, id, revision}], conflicts: [...], newRevision }
```

- `id` is generated by the client (UUIDv7), so a row exists locally before the
  server has seen it.
- `baseRevision` is the revision the client was editing. Omit it for a create.
- Ops are applied in FK dependency order (accounts and categories, then
  transactions, then budgets and investments) regardless of how they are
  listed, so a batch that creates an account and a transaction referencing it
  works either way round.
- The whole batch is one transaction. A batch that half-applied would leave a
  transaction pointing at an account that never landed.
- Batches are capped at 500 ops so one client cannot hold a write transaction
  open indefinitely.
- `householdId` in a payload is ignored. Scoping comes from the caller's
  verified membership.

## Conflict rules

| Situation | Outcome |
| --- | --- |
| Two offline **creates** | Never conflict — client-generated ids mean they are genuinely two rows |
| Concurrent **edits** | The later arrival takes the row; the value it overwrote is kept in `SyncConflict` |
| **Delete** vs concurrent edit | The delete wins. Resurrecting a row somebody deliberately deleted is worse than losing an edit to it |
| Edit arriving for a **deleted** row | Rejected, and recorded as a conflict for review |

Field-level merging (CRDT) is deliberately **not** used. A transaction is a
small, atomic, human-authored record; merging one device's amount with
another's category produces a row neither person entered.

```
GET  /api/v1/sync/conflicts
POST /api/v1/sync/conflicts/:id/resolve
```

## Tombstones

A deleted row is kept with `deletedAt` set so other devices learn it is gone.
It is hard-deleted only once no `SyncCursor` could still need it — otherwise a
device offline for a month comes back, never learns about the delete, and
re-creates the row from its own copy. Households with no registered device are
skipped rather than swept eagerly.

```
GET /api/cron/sweep-tombstones?olderThanDays=30
    Authorization: Bearer $CRON_SECRET
```

## Performance

The pull is a single ordered index scan per entity against
`(householdId, revision, id)`, using a SQL row comparison
(`(revision, id) > (r, i)`).

Prisma can only express that as `revision > r OR (revision = r AND id > i)`,
which Postgres answers with a bitmap scan and a full sort. Measured on 20k
transactions (10k in the household under test, 10k in a neighbour):

| Query | Plan | Time | Buffers |
| --- | --- | --- | --- |
| Prisma OR form, `(householdId, revision)` | Bitmap Heap Scan + Sort | 1.24 ms | 32 |
| Row comparison, `(householdId, revision)` | Index Scan + Incremental Sort | 0.59 ms | — |
| Row comparison, `(householdId, revision, id)` | **Index Only Scan, no sort** | **0.20 ms** | **5** |

Hence the raw cursor query and the three-column index. Rows are then fetched
through the normal client, because narrative fields are encrypted at rest and a
raw row would hand the device ciphertext.

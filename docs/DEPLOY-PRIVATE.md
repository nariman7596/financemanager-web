# دیپلوی خصوصی — اپ روی اینترنت باز نمی‌شود

برای وقتی که سرورت کارِ دیگری هم می‌کند (مثلاً VPN روی ۴۴۳) و **نمی‌خواهی دادهٔ مالی‌ات
هیچ دری به اینترنت داشته باشد.**

اپ فقط روی `127.0.0.1:3000` سرورگوش می‌دهد. نه دامنه، نه رکوردِ DNS، نه گواهی در
لاگ‌های عمومیِ Certificate Transparency، نه پورتِ باز. Postgres هم مثل همیشه روی
شبکه‌ی داخلیِ داکر می‌ماند و اصلاً منتشر نمی‌شود.

---

## ۰. اول این را بخوان: سرورت چقدر رم دارد؟

```bash
free -h && nproc
```

| رم | مسیرِ درست |
|---|---|
| **< ۲ گیگ** یا **۱ هسته** | ⚠️ **روی سرور build نکن** — برو بخشِ «۱-ب» |
| ۴ گیگ به بالا | می‌توانی روی خودِ سرور build کنی — بخشِ «۱-الف» |

**چرا:** بیلدِ پروداکشنِ Next.js چند گیگ رم می‌خواهد. روی یک VPS با ۱ گیگ رم و
یک هسته، بیلد تمام نمی‌شود؛ سیستم شروع می‌کند به swap-زدن و در نهایت OOM killer
حتی SSH را هم می‌کُشد. **اجرا کردنِ اپ اما ارزان است** (~۲۵۰ مگ) — فقط ساختنش سنگین است.

### ⚙️ در هر دو حالت: swap اضافه کن
سرورهای کوچک معمولاً swap ندارند. این کار یک شبکه‌ی ایمنی می‌سازد که جلوی
کشته‌شدنِ ناگهانیِ سرویس‌ها را بگیرد:

```bash
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
free -h
```

## ۱-ب. بالا آوردن با ایمیجِ آماده — **توصیه‌شده برای سرورِ کوچک**

بیلد روی رانرهای گیت‌هاب انجام می‌شود (۴ هسته، ۱۶ گیگ رم) و سرور فقط ایمیجِ
آماده را `pull` می‌کند: چند ثانیه، بدونِ فشار روی رم.

**یک‌بار روی گیت‌هاب:**
1. فایلِ `.github/workflows/build-image.yml` از قبل در ریپو هست. با اولین push
   به `main` خودش اجرا می‌شود — یا از تبِ **Actions** دستی اجرایش کن
   (**Build and publish image** → *Run workflow*).
2. صبر کن تا سبز شود (~۵–۱۰ دقیقه). ایمیج می‌رود به
   `ghcr.io/nariman7596/financemanager-web:latest`.
3. **دسترسیِ ایمیج:** اگر بسته (package) خصوصی باشد، سرور برای pull باید لاگین کند.
   ساده‌ترین راه: در صفحه‌ی **Packages** ریپو، بسته را روی **Public** بگذار.
   یا اگر می‌خواهی خصوصی بماند، روی سرور:
   ```bash
   echo "GHCR_PAT" | docker login ghcr.io -u nariman7596 --password-stdin
   ```
   (توکن با دسترسیِ `read:packages` از github.com/settings/tokens)

**روی سرور:**
```bash
git clone https://github.com/nariman7596/financemanager-web.git
cd financemanager-web
cp .env.docker.example .env
nano .env          # DB_PASSWORD / AUTH_SECRET / CRON_SECRET

docker compose -f docker-compose.ghcr.yml pull
docker compose -f docker-compose.ghcr.yml up -d
```

**بروزرسانی از این به بعد** (به‌جای یک ساعت بیلد):
```bash
git pull
docker compose -f docker-compose.ghcr.yml pull
docker compose -f docker-compose.ghcr.yml up -d
```

> در ادامه‌ی این سند هر جا `docker-compose.private.yml` دیدی، اگر مسیرِ «۱-ب» را
> رفته‌ای همان دستور را با `docker-compose.ghcr.yml` بزن.

بررسی:
```bash
docker compose -f docker-compose.private.yml ps
curl -I http://127.0.0.1:3000/login        # انتظار: HTTP 200
sudo ss -tlnp | grep 3000                  # باید 127.0.0.1:3000 باشد، نه 0.0.0.0
```

> ⚠️ اگر خروجی `0.0.0.0:3000` بود یعنی فایلِ اشتباهی را اجرا کرده‌ای. داکر پورت‌های
> منتشرشده را **از فایروال رد می‌کند** (روی زنجیره‌ی `DOCKER` در iptables می‌نشیند)،
> پس `ufw deny 3000` جلویش را نمی‌گیرد. پیشوندِ `127.0.0.1:` تنها چیزی است که کار می‌کند.

**هیچ پورتی در فایروال باز نکن.** فقط SSH.

## 🍪 نکته‌ی مهم: کوکیِ نشست و HTTPS

اپ کوکیِ نشست را با فلگِ `Secure` می‌فرستد، و مرورگر کوکیِ Secure را روی `http://`
معمولی **نمی‌فرستد** — یعنی لاگین می‌کنی ولی بلافاصله به صفحه‌ی ورود برمی‌گردی، بی‌آنکه
خطایی ببینی.

استثنا: مرورگرها **`localhost` را «امن» حساب می‌کنند.**

| روشِ دسترسی | آدرس | کوکی کار می‌کند؟ |
|---|---|---|
| تونلِ SSH | `http://localhost:3000` | ✅ بله (بدونِ هیچ تنظیمی) |
| WireGuard / تیل‌اسکیل | `http://10.66.66.1:3000` | ❌ نه — مگر `COOKIE_SECURE=false` |

برای حالتِ دوم، در `.env` این را اضافه کن و کانتینر را ری‌استارت کن:
```ini
COOKIE_SECURE=false
```
```bash
docker compose -f docker-compose.private.yml up -d
```

> 🔒 **این فقط برای همین سناریو بی‌خطر است**، چون اپ اصلاً روی اینترنت نیست و ترافیک
> داخلِ تونلِ رمزنگاری‌شده‌ی خودت جابه‌جا می‌شود. **روی نسخه‌ی عمومی هرگز این را نگذار** —
> توکنِ نشست به‌صورتِ متنِ ساده منتقل می‌شود.

## ۲. راه‌های دسترسی

### الف) تونلِ SSH — ساده‌ترین و مطمئن‌ترین (لپ‌تاپ)

هیچ تنظیمی روی سرور نمی‌خواهد. روی کامپیوترِ خودت:

```bash
ssh -N -L 3000:127.0.0.1:3000 root@216.126.229.4
```

بعد در مرورگر: **<http://localhost:3000>** — کوکی هم بدونِ دردسر کار می‌کند.

میان‌بر: در `~/.ssh/config` بگذار
```
Host fm
    HostName 216.126.229.4
    User root
    LocalForward 3000 127.0.0.1:3000
```
از این به بعد فقط `ssh -N fm`.

### ب) WireGuard — برای گوشی (توصیه‌شده)

Xray تو **TCP/443** است؛ WireGuard روی **UDP** کار می‌کند، پس **هیچ تداخلی با VPN فعلی‌ات
ندارد** و می‌توانند کنار هم باشند.

```bash
# روی سرور
curl -O https://raw.githubusercontent.com/angristan/wireguard-install/master/wireguard-install.sh
chmod +x wireguard-install.sh && sudo ./wireguard-install.sh
# پورتِ پیشنهادی: مثلاً 51820/udp — و در فایروال بازش کن:
sudo ufw allow 51820/udp
```

اسکریپت برایت QR می‌سازد؛ با اپِ WireGuard روی گوشی اسکنش کن.

**در کانفیگِ کلاینت `AllowedIPs` را به `10.66.66.0/24` تغییر بده** (پیش‌فرضِ اسکریپت
`0.0.0.0/0` است، یعنی *همه‌ی* ترافیکِ گوشی از این تونل می‌رود و با Xray سرِ جنگ
پیدا می‌کند). با `10.66.66.0/24` فقط ترافیکِ همین اپ از تونل می‌رود.

#### ⚠️ گامی که فراموشش می‌کنی: بایندِ اپ

اپ به‌صورتِ پیش‌فرض روی **`127.0.0.1:3000`** گوش می‌دهد. یک کلاینتِ WireGuard که از
`wg0` وارد می‌شود **نمی‌تواند** به سوکتی که به لوپ‌بک بایند شده وصل شود — همان چیزی که
اپ را خصوصی نگه می‌دارد، جلوی گوشی را هم می‌گیرد. در `.env`:

```ini
APP_BIND=10.66.66.1
COOKIE_SECURE=false
```

```bash
docker compose -f docker-compose.ghcr.yml up -d
sudo ss -tlnp | grep 3000     # باید 10.66.66.1:3000 باشد، نه 0.0.0.0
```

این هنوز خصوصی است: `wg0` فقط داخلِ تونل وجود دارد و روی اینترنت دیده نمی‌شود.
`COOKIE_SECURE=false` هم لازم است چون `10.66.66.1` مرورگر را «امن» حساب نمی‌کند (بالا).

بعد در مرورگرِ گوشی: <http://10.66.66.1:3000>

#### عیب‌یابی

**۱. اپِ WireGuard می‌گوید وصل است ولی آدرس باز نمی‌شود.**
اول ببین واقعاً هندشیک شده یا نه. در اپِ WireGuard رویِ گوشی به آمارِ ترافیک نگاه کن:

| نشانه | معنی |
|---|---|
| ارسال چند کیلوبایت، **دریافت ۰** | هندشیک انجام **نشده** — بسته‌ها می‌روند، جوابی نمی‌آید. مشکل شبکه/فایروال است، نه اپ |
| هر دو در حالِ رشد، ولی صفحه باز نمی‌شود | تونل سالم است؛ مشکل بایندِ اپ است (بالا) |

برای حالتِ اول، روی سرور:
```bash
sudo wg show                      # latest handshake چه می‌گوید؟
sudo ufw status | grep 51820      # پورت باز است؟
sudo ss -ulnp | grep 51820        # wireguard واقعاً گوش می‌دهد؟
```

**۲. هندشیک اصلاً انجام نمی‌شود (دریافت ۰).**
اگر پورت باز است و سرویس بالاست، به احتمالِ زیاد **UDP در مسیرِ ایران فیلتر/دراپ
می‌شود**. WireGuard امضایِ ثابتی دارد و DPI راحت می‌شناسدش. دو راهِ عملی:

- پورت را به **`443/udp`** ببر. با Xray (که TCP/443 است) تداخل ندارد و ترافیکِ
  UDP/443 شبیهِ QUIC است، پس کمتر دراپ می‌شود:
  ```bash
  sudo sed -i 's/^ListenPort = .*/ListenPort = 443/' /etc/wireguard/wg0.conf
  sudo ufw allow 443/udp
  sudo systemctl restart wg-quick@wg0
  ```
  در کانفیگِ گوشی هم `Endpoint` را به `<ip>:443` عوض کن.
- اگر باز هم نشد، WireGuard را ول کن و از **همان Xray که مطمئناً کار می‌کند** استفاده
  کن (بخشِ «د» پایین).

> ℹ️ برای لپ‌تاپ همیشه تونلِ SSH (الف) ساده‌تر و مطمئن‌تر است. WireGuard فقط برای
> گوشی ارزشِ دردسر را دارد.

### د) تونلِ SSH از روی گوشی — وقتی WireGuard جواب نمی‌دهد

مطمئن‌ترین راه، و **بدونِ هیچ تغییری روی سرور**. SSH روی TCP است (نه UDP) و از همان
مسیری می‌رود که الان با لپ‌تاپ به سرور وصل می‌شوی — یعنی ثابت‌شده کار می‌کند.

یک کلاینتِ SSH با port-forwarding روی گوشی نصب کن (Termius روی هر دو پلتفرم، یا
ConnectBot روی اندروید — رایگان)، و یک هاست بساز:

| فیلد | مقدار |
|---|---|
| Host | `216.126.229.4` |
| User | `root` |
| Port forwarding | **Local**، `3000` → `127.0.0.1:3000` |

وصل شو، بعد در مرورگرِ گوشی: <http://localhost:3000>

دو مزیتِ مهم:
- `APP_BIND` را **لازم نداری** — تونل به لوپ‌بکِ خودِ سرور می‌خورد، همان‌جا که اپ
  پیش‌فرض گوش می‌دهد.
- `COOKIE_SECURE=false` هم لازم نیست، چون مرورگر `localhost` را «امن» حساب می‌کند.

یعنی امن‌ترین حالت هم همین است: نه پورتی باز می‌شود، نه کوکی از حالتِ Secure درمی‌آید.
تنها هزینه‌اش این است که هر بار باید اول SSH را وصل کنی.

### ج) تیل‌اسکیل — بی‌دردسرترین، ولی وابسته به سرویسِ ثالث
`curl -fsSL https://tailscale.com/install.sh | sh` روی سرور و گوشی، بعد
`http://<tailscale-ip>:3000`. نیازی به بازکردنِ هیچ پورتی نیست.
⚠️ نیازمندِ حسابِ تیل‌اسکیل است و ممکن است از ایران در دسترس نباشد.

## ۳. بکاپ (این را جدی بگیر)

دادهٔ مالی‌ات فقط روی همین سرور است. **راهنمای کامل: [`BACKUP.md`](./BACKUP.md)**

```bash
chmod +x deploy/backup.sh deploy/restore.sh
./deploy/backup.sh          # یک‌بار دستی، برای اطمینان
crontab -e
```
```cron
30 3 * * * /bin/bash /root/financemanager-web/deploy/backup.sh >/dev/null 2>&1
```

> ⚠️ **از الگوی رایجِ `pg_dump | gzip > out.gz && find … -delete` استفاده نکن.** اگر
> `pg_dump` شکست بخورد، `gzip` همچنان یک آرشیوِ معتبرِ **خالی** می‌سازد، `&&` موفق
> حساب می‌شود و مرحله‌ی حذف بکاپ‌های سالم را پاک می‌کند. `deploy/backup.sh` با
> `pipefail`، بررسیِ محتوا و حذفِ فقط‌پس‌از‌تأیید این را می‌بندد.

بازگردانی (اسنپ‌شات می‌گیرد و تأیید می‌خواهد):
```bash
./deploy/restore.sh ~/backups/fm-<تاریخ>.sql.gz
```

**و یک نسخه بیرون از سرور نگه دار** — بکاپی که روی همان دیسکِ در‌معرضِ‌خرابی است،
نصفِ بکاپ است. روی کامپیوترِ خودت (نه روی سرور):
```bash
scp root@<server-ip>:'/root/backups/fm-*.sql.gz' ~/fm-backups/
```

## ۴. دستورهای روزمره

```bash
cd ~/financemanager-web
# اگر مسیرِ «۱-ب» را رفته‌ای، docker-compose.ghcr.yml را بگذار
C="docker compose -f docker-compose.ghcr.yml"

$C ps                    # وضعیت
$C logs -f app           # لاگِ اپ
$C logs app | grep -i migrat   # آیا مایگریشن‌ها اجرا شدند؟
$C restart app           # ری‌استارت
git pull && $C pull && $C up -d   # بروزرسانی (مسیرِ ایمیجِ آماده)
```

## عیب‌یابی

| علامت | علت |
|---|---|
| لاگین می‌کنم ولی برمی‌گردم به صفحه‌ی ورود | کوکیِ Secure. یا از `localhost` وارد شو یا `COOKIE_SECURE=false` بگذار |
| با تونلِ SSH باز می‌شود ولی از روی VPN نه | اپ به `127.0.0.1` بایند است. `APP_BIND=10.66.66.1` بگذار و `up -d` بزن |
| اپِ WireGuard وصل است ولی ارسال دارد و **دریافتِ ۰** | هندشیک نشده؛ تونل واقعاً بالا نیست. بخشِ «ب / عیب‌یابی» را ببین |
| `curl` روی ۳۰۰۰ جواب نمی‌دهد | `$C ps` — احتمالاً اپ بالا نیامده؛ لاگ را ببین |
| `ss` می‌گوید `0.0.0.0:3000` | `APP_BIND` را روی `0.0.0.0` گذاشته‌ای، یا فایلِ اشتباهی اجرا شده — پورت نباید روی اینترنت باشد |
| صفحات خطای دیتابیس می‌دهند | مایگریشن اجرا نشده: `$C logs app \| grep -i migrat` |
| بعد از ری‌استارتِ سرور بالا نیامد | `restart: unless-stopped` هست؛ چک کن داکر خودش enable باشد: `sudo systemctl enable docker` |

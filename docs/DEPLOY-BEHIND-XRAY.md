# دیپلوی وقتی Xray/V2Ray روی پورت ۴۴۳ نشسته

اگر روی همان VPS یک VPN (Xray / V2Ray / Sing-box / Trojan) روی **TCP/443** داری،
Caddy نمی‌تواند ۴۴۳ را بگیرد. این سند دو مسیر دارد:

| مرحله | نتیجه | ریسکِ VPN |
|---|---|---|
| **۱** | اپ روی `https://finance.example.com:8443` | **صفر** — کانفیگِ VPN دست نمی‌خورد |
| **۲** | اپ روی `https://finance.example.com` (بدونِ پورت) | نیازمندِ تغییر در کانفیگِ Xray |

> 💡 **اول مرحله ۱ را انجام بده.** ظرفِ ده دقیقه اپِ کارکننده داری، بدونِ اینکه به یک
> VPNِ سالم دست بزنی. مرحله ۲ صرفاً زیباسازیِ آدرس است، نه ضرورت.

---

## 🔍 اول: ببین دقیقاً چه چیزی کجاست

```bash
# چه چیزی روی این پورت‌ها گوش می‌دهد؟
sudo ss -tlnp | grep -E ':(80|443|8080|8443)\s'

# Xray در حالتِ Reality است یا TLS کلاسیک؟
sudo grep -oE '"(security|dest|serverNames|certificateFile|fallbacks)"[^,]*' \
  /usr/local/etc/xray/config.json
```

دو چیزِ حیاتی از این خروجی درمی‌آید:

1. **پورت ۸۰ آزاد است؟** برای گرفتنِ گواهیِ خودکار (چالشِ HTTP-01) لازم است.
   اگر اشغال باشد باید از چالشِ DNS-01 استفاده کنیم.
2. **`"security": "reality"` یا `"security": "tls"`؟** ← این تعیین می‌کند مرحله ۲ ممکن
   است یا نه (پایین توضیح داده شده).

---

## مرحله ۱ — اپ روی پورت ۸۴۴۳ (بی‌ریسک)

Xray دست‌نخورده روی ۴۴۳ می‌ماند. Caddy روی **۸۴۴۳** سرو می‌کند و گواهی را از طریقِ
پورتِ ۸۰ می‌گیرد.

### ۱.۱ فایروال
```bash
sudo ufw allow 80
sudo ufw allow 8443
```

### ۱.۲ کانفیگِ پراکسی
در `deploy/proxy/Caddyfile`:
```caddy
finance.example.com:8443 {
	reverse_proxy financemanager:3000
}
```

در `deploy/proxy/docker-compose.yml` بخشِ `ports` را این کن:
```yaml
    ports:
      - "80:80"        # فقط برای گرفتن و تمدیدِ خودکارِ گواهی (ACME HTTP-01)
      - "8443:8443"    # خودِ اپ
```

> ⚠️ پورتِ ۸۰ باید **باز بماند** — Let's Encrypt هر ۶۰ روز برای تمدید سراغش می‌آید.
> اگر ببندی، گواهی بعد از ۹۰ روز منقضی می‌شود.

### ۱.۳ بالا آوردن
```bash
docker network create web            # اگر قبلاً نساخته‌ای
cd ~/financemanager-web/deploy/proxy && docker compose up -d
cd ~/financemanager-web && docker compose up -d --build
```

### ۱.۴ تست
```
https://finance.example.com:8443
```

> **اگر پورتِ ۸۰ هم اشغال بود:** چالشِ HTTP-01 کار نمی‌کند. آن‌وقت باید از **DNS-01**
> استفاده کنیم که به هیچ پورتی نیاز ندارد، ولی به توکنِ API ارائه‌دهنده‌ی DNS و ایمیجِ
> Caddy با پلاگینِ همان ارائه‌دهنده نیاز دارد. اگر به این‌جا رسیدی بگو تا تنظیمش کنم.

---

## مرحله ۲ — آدرسِ تمیز روی ۴۴۳

اینجا Xray مالکِ ۴۴۳ می‌ماند و ترافیکی که VPN نیست را به Caddy **پاس می‌دهد**
(قابلیتِ `fallbacks`). این دقیقاً همان چیزی است که سایتِ پوششیِ Xray را می‌سازد.

### 🚩 اول این را چک کن: Reality یا TLS؟

| حالت | مرحله ۲ ممکن است؟ |
|---|---|
| `"security": "tls"` (گواهیِ واقعی، `certificateFile` دارد) | ✅ بله — با `fallbacks` |
| `"security": "reality"` | ❌ نه به این شکل — پایین را بخوان |

**چرا Reality فرق دارد:** Reality گواهیِ واقعیِ خودت را ارائه نمی‌کند؛ TLS یک سایتِ
دیگر را قرض می‌گیرد. پس نمی‌تواند `https://finance.example.com` را با گواهیِ معتبرِ
دامنه‌ی خودت سرو کند. مرورگر خطای گواهی می‌دهد. با Reality گزینه‌ها این‌هاست:
- **همان مرحله ۱ را نگه دار** (ساده‌ترین و توصیه‌شده)
- یا یک **مسیریابِ SNI** (مثلِ HAProxy یا sing-box) جلوی هر دو بگذاری که بر اساسِ
  نامِ دامنه ترافیک را بینِ Xray و Caddy تقسیم کند — کارآمد ولی یک قطعه‌ی متحرکِ
  بیشتر و ریسکِ قطعیِ VPN حینِ تنظیم.

### ۲.۱ اگر TLS کلاسیک داری

**الف) از کانفیگِ Xray بکاپ بگیر** (این مهم‌ترین قدم است):
```bash
sudo cp /usr/local/etc/xray/config.json ~/xray-config.backup.json
```

**ب)** در اینباندِ ۴۴۳، به `settings` این را اضافه کن:
```json
"fallbacks": [
  { "dest": "127.0.0.1:8080", "xver": 1 }
]
```

**ج)** مطمئن شو گواهیِ Xray دامنه‌ی اپ را هم پوشش می‌دهد (یا همان دامنه باشد، یا
گواهیِ SAN، یا یک ورودیِ دوم در آرایه‌ی `certificates`).

**د)** حالا TLS را Xray تمام می‌کند، پس Caddy باید **HTTP ساده** بدهد:

`deploy/proxy/Caddyfile`:
```caddy
{
	servers {
		# چون Xray با xver:1 پروتکلِ PROXY می‌فرستد، تا IP واقعیِ کاربر حفظ شود
		trusted_proxies static 127.0.0.1/32
	}
}

http://finance.example.com:8080 {
	reverse_proxy financemanager:3000
}
```

`deploy/proxy/docker-compose.yml`:
```yaml
    ports:
      - "127.0.0.1:8080:8080"   # فقط روی لوکال‌هاست — از بیرون در دسترس نیست
```

**ه)** تست و اعمال:
```bash
sudo xray -test -c /usr/local/etc/xray/config.json   # اول اعتبارسنجی!
sudo systemctl restart xray
sudo systemctl status xray                            # باید active باشد
```

> 🔴 **قبل از ری‌استارت، حتماً یک سشنِ SSH بازِ دیگر داشته باش.** اگر کانفیگ خراب شود و
> VPN بالا نیاید، تنها راهِ برگشتت SSH است:
> `sudo cp ~/xray-config.backup.json /usr/local/etc/xray/config.json && sudo systemctl restart xray`

## 🔐 چند نکته‌ی امنیتی (دادهٔ مالی است)

- پورتِ Postgres هرگز روی هاست منتشر نمی‌شود — در `docker-compose.yml` روی شبکه‌ی
  `internal` است. همین‌طور نگهش دار.
- `AUTH_SECRET` را بینِ دیپلوی‌ها ثابت نگه دار، وگرنه همه‌ی نشست‌ها باطل می‌شوند.
- بکاپِ شبانه‌ی دیتابیس را راه بینداز (`docs/VPS.md`، بخشِ Backups).
- اگر خواستی حتی امن‌تر: در Caddy دسترسی را به IPهای مشخص محدود کن، یا اپ را فقط
  از داخلِ VPN در دسترس بگذار (آن‌وقت اصلاً نیازی به پورتِ عمومی نیست).

## عیب‌یابی

| علامت | علت |
|---|---|
| گواهی گرفته نمی‌شود | پورتِ ۸۰ بسته یا اشغال است؛ یا رکوردِ A هنوز منتشر نشده |
| `502` از Caddy | کانتینرِ اپ بالا نیست: `docker compose logs -f app` |
| بعد از تغییرِ Xray، VPN قطع شد | بکاپ را برگردان (بالا) و بگو تا با هم دیباگ کنیم |
| اپ بالا می‌آید ولی همه‌ی صفحات خطا | جدول‌ها ساخته نشده‌اند: `docker compose logs app \| grep -i migrat` |
